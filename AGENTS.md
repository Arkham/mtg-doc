# AGENTS.md

Guidance for anyone (human or agent) working on **mtg-doc**: a local web app that reads a Commander
deck from a photo or list, optimizes it within a bracket and budget, and publishes read-only reports
as a static site.

## Commands

```bash
pnpm dev              # API + Vite, Elm hot-reloaded by elm-watch, on http://localhost:5173 (HOST=0.0.0.0 for your phone)
pnpm check            # format:check + lint + typecheck + generated Elm up to date + all unit tests. Run before every push.
pnpm test             # unit + integration tests (offline, ~seconds)
pnpm test:elm         # Elm unit tests (tests/, elm-test-rs)
pnpm test:e2e         # Playwright: local app flow + static site on desktop, iPhone and iPad (WebKit)
pnpm test:visual      # every page and state, desktop/iPhone/iPad: exact DOM + screenshots vs committed baselines
pnpm test:live        # the real Scryfall, Spellbook and EDHREC through the app's clients (needs network; not in CI)
pnpm fakes:cards "Name" ...  # add real cards to the fake Scryfall's database (needs network)
pnpm format           # prettier --write + elm-format
pnpm lint             # oxlint + elm-review
pnpm typecheck        # tsc --noEmit (TypeScript 7); Elm is checked by its compiler in every build and test
pnpm gen:elm          # regenerate src/web/Types.elm (decoders) and src/web/Symbols.elm from the TypeScript (--check in CI)
pnpm build:static     # read-only site into site/ (see README for --only/--out)
pnpm check:decks      # every saved report agrees with its deck list in every section
pnpm fix:contradictions   # fix what saved reports' model-written texts say that the facts contradict (needs an LLM; --dry-run, --only)
pnpm write:guides     # (re)write saved decks' how-to-play guides (needs an LLM; --only); run fix:contradictions after
pnpm mark:cards       # mark card references ([[Name]]) in saved reports written before copy had them (needs an LLM)
```

CI (`.github/workflows/ci.yml`) runs all of the above, including the e2e suite, on every push and PR.
The visual suite's baselines depend on the OS's font rendering, so it runs locally.
Pages (`.github/workflows/pages.yml`) deploys `main`.

## Layout

```
src/
  server/          Express API, optimizer pipeline and data sources (Node, run with tsx)
    analysis/      pure logic: roles, mana, simulator, bracket rules, solver, optimizer helpers
    sources/       Scryfall, EDHREC, Commander Spellbook, web research clients
    llm.ts         the only place that talks to the LLM (OpenAI Responses API)
    pipeline.ts    orchestrates a job: a task graph from loading the deck to writing the report
  shared/          what server and UI share: types.ts (the UI's Elm types are generated from it)
  web/             the UI, in Elm (local app + static site, switched by the isStatic flag)
    Main.elm       the app: pages, overlays, ports; Page/ for each page, Ui/ for shared views
    Types.elm      generated by scripts/gen-elm.ts: types, decoders and encoders (don't edit)
    main.ts        boots Elm, owns the URL (nav.ts, routes.ts) and the ports
    elements.ts    custom elements for what Elm can't do from a view (focus, clipboard, tilt, ...)
tests/             *Test.elm (Elm unit tests); unit/, integration/, e2e/ and visual/ (Playwright), live/;
                   fixtures/ (the fakes' data, sample decks) and support/ (helpers, test servers)
scripts/           build-static.ts, gen-elm.ts, elm.ts (builds the Elm app), benchmarks
decks/             user decks, one folder per commander (initial.txt, optimized.txt, report.*, cards.json, run.json)
```

## Development practices

### Correctness first

- Every card that enters a deck is validated: legal in Commander, inside the commander's color identity,
  singleton (basics excepted), under budget, not locked, and inside the target bracket. New code paths
  that add cards must go through the same `violation` check (`makeViolation` in `src/server/analysis/search.ts`).
- Bracket rules live in one table (`BRACKETS` in `src/server/analysis/bracket.ts`), sourced from the
  official Commander Brackets. Game Changers come from Scryfall's live data; never hard-code the list.
- The final deck is always re-verified (Commander Spellbook + simulator). Don't trust the LLM's claims:
  it proposes and explains; deterministic code decides and enforces.
- Before a report is written, the pipeline checks its model-written texts (strategy, swap reasons,
  synergies) against the facts deterministic code established (`src/server/contradictions.ts`): two
  reads per few texts find contradictions and drafting leftovers ("keep the proposal"), `decide`
  confirms each and its fix, and a fix may never bring in a card the text didn't name. Run
  `pnpm fix:contradictions` after changing how texts are written.
- Prices use Scryfall, falling back to the cheapest printing with a USD price. A card must never look
  free because its default printing lacks a price.
- Respect Scryfall's rate limits (2/s for search, named and collection; 10/s otherwise; a 429 means
  back off 30s). Batch: `/cards/collection` takes 75 cards, and searches can `or` many names together.

### LLM usage

- All LLM calls go through `src/server/llm.ts`: `chatJson` (Responses API, zod-validated structured
  output; `chatJsonStream` is the same with the answer streamed as it's written), `webSearch` (Responses API `web_search` tool, with citations) and `decide` (Decisions API:
  calibrated yes/no probabilities, e.g. "is this card in this crop?"). No other module calls the LLM.
- One model (`LLM_MODEL`) does every task, at `LLM_REASONING` (low by default). Don't pick models
  per task in code, and never write a model's name in the codebase (code, tests, docs): models are
  configuration. `LLM_SERVICE_TIER`, when set, goes with every Responses API request.
- Use `decide` for any yes/no judgement (is this real, does the user agree, is this worth doing)
  rather than asking `chatJson` for a boolean. It falls back to the regular model when the
  Decisions API is off (`LLM_DECISIONS=false`) or fails, so callers never handle that themselves.
  Today it verifies scanned cards and model-proposed synergies, confirms replies to the doc's
  proposals, and judges whether a change is worth a re-run.
- Never trust a single model read: photo recognition votes across independent passes (whole photo +
  two tilings) and verifies anything only one pass saw. Keep that shape when changing the scanner, and
  measure changes with `node --import tsx scripts/ocr-bench.ts photo.jpg [--truth list.txt]`.
- Keep the codebase provider-neutral: configure through `LLM_BASE_URL` / `LLM_API_KEY` / `LLM_MODEL`;
  no vendor- or company-specific names, URLs or keys in code, docs or tests. Real endpoints and keys
  belong in the gitignored `.env` (which supports `${VAR}` references to shell variables).
- The app must keep working without an LLM (pasted lists, data-only swaps).

### Chat parity

- Anything the report UI can change, the user must also be able to do by asking the doc in chat:
  card edits, applying suggestions, re-running the optimizer with any setting, refreshing derived
  data. When you add a button or form that changes a deck or its report, extend `src/server/chat.ts`
  (reply schema, deck context and system prompt) in the same change, and add a case to the
  "everything the report UI can change, the chat can too" test in `tests/integration/llm-pipeline.test.ts`.
- The chat follows the view: on "Your deck" it talks about and edits the list as submitted
  (`initial.txt`), and the suggested deck is rebuilt from it with the swaps that still apply
  (`rebaseSwaps`); on the optimized view it edits the suggestions. When the user asks to change
  the other list ("in my deck"), the reply's `target` says so and the changes edit that one.
- Every swap the doc suggests (its swaps, and suggested land swaps) has an Apply button that makes
  it in the deck as submitted (`applySwap`, `applyManaSuggestion`), leaving the suggested deck as
  it was. Swaps the edit carries out are settled (`realizedSwaps`, `onSubmittedList`), not
  dropped, so they're neither made twice nor counted as broken.
- Destructive or slow chat actions (re-running the optimizer, anything that replaces the list) are
  proposed first and start only once the user confirms, by button or by a reply the Decisions API
  judges as a yes. Cheap, non-destructive ones (like finding synergies again) can run directly.
  A yes to proposed card changes applies them, like the Apply button.
- Every change to a deck's report (chat edits, Apply buttons, re-runs, synergy searches) runs in
  the deck's edit queue (`src/server/edit-queue.ts`): the API answers at once with an edit id, the
  queue runs a deck's edits one at a time in order, and the UI polls until they're in. New code
  that writes a report must go through it too, and write files with `writeAtomic`.
- An edit is quick: the list and everything that follows from it alone (stats, simulation,
  bracket from the last estimate, combos and synergies that still hold, land swaps that still
  apply) go in at once, with no request out: it works from the deck's saved cards (`cards.json`,
  every card in both lists, written by each run and edit through `writeCards`; `loadDeck` reads it
  and fetches only what's missing), and a card it adds that the deck already knows takes its
  bracket flags from the report's assessments. Only cards new to the deck reach Scryfall and
  Spellbook; a run fetches everything afresh (`fresh`). What needs Commander Spellbook,
  Scryfall searches or the model (bracket estimate, combo search, land suggestions, synergies
  with new cards, guides, the contradiction check) is a refresh (`src/server/refresh.ts`) that runs once edits stop for `REFRESH_DELAY_MS`
  (30s); every edit pushes it back, so a run of edits is worked out once. It computes outside the
  queue and saves only if no edit came in meanwhile, so edits never wait for it. Pending
  refreshes are kept in the deck's `refresh.json` and resume after a restart; a full re-run
  supersedes them. When you add a report field that needs an outside service or the model, work
  it out in the refresh, and keep the quick edit consistent without it.
- Once an edit's refresh is in, the doc checks what the edits made worse in the optimizer's
  terms (`worsenedSince`, from the gaps the deck had before the first of them: lands, color
  sources, roles, bracket checks, budget, dropped suggestions) and `decide`s whether a re-run is
  worth it (without an LLM, any such gap is). If so it proposes a re-run that keeps the user's
  edits (`keepEdits`: chat's swaps are pinned, their adds locked and their cuts excluded), with a
  button to confirm.
- Importing a deck (photo or list, the review screen) happens before the deck exists, so it's out
  of scope.
- A chat edit updates every section that names the cards it touches, not just the list: stats,
  bracket (including its skipped and Game Changer lists), combos, mana suggestions, swaps (which
  must always equal the net difference from the submitted list), synergies (dropped when a card
  leaves, searched for when one arrives) and card previews. All edits go through
  `applyDeckChanges` (`src/server/chat.ts`); the pure reconciliation lives in
  `src/server/analysis/reconcile.ts`. When you add a report field that names deck cards, update it
  there too, and teach `checkReport` (`src/server/analysis/consistency.ts`) to verify it.
- `writeResults` refuses to save a report that `checkReport` finds inconsistent, and a unit test runs
  it on every deck in `decks/`. After touching a report by hand or by script, run `pnpm check:decks`.

### Testing

- Tests are offline and deterministic. Scryfall, Commander Spellbook and EDHREC are fakes
  (`tests/support/fakes`) that answer any request from small databases of real data in
  `tests/fixtures/fakes`: cards trimmed to the fields the app reads, a list of real combos and of
  the cards Spellbook flags, and EDHREC commander pages. They work out answers rather than replay
  them, so how the app batches, orders or times its requests doesn't matter; a request they don't
  model fails loudly. A test that needs a card the database lacks adds it with `pnpm fakes:cards`;
  combos and flags are added by hand. When a client of an outside service changes, run
  `pnpm test:live` against the real one, and update its fake to match.
- Import `tests/support/env.ts` first in every Node test: it isolates tests from `.env`, disables the
  LLM, installs the fakes and runs edits' refreshes right away (`whenIdle` waits for them). Stub the LLM endpoint explicitly when testing LLM code.
- Unit-test pure logic in `src/server/analysis` directly with the factories in `tests/support/cards.ts`.
  Integration tests cover the full pipeline, the HTTP API and the static build. Playwright covers the
  UI, including touch behaviour on iPhone/iPad and checks for horizontal overflow on phones.
- Elm logic gets elm-test tests in `tests/`. Anything Elm must agree on with the server or with
  JavaScript (decoding saved reports, number formatting, sorting, links) is checked against the
  real thing in `tests/unit/elm-parity.test.ts`.
- `pnpm test:visual` compares every page and state with committed baselines: the rendered DOM
  exactly, and screenshots. A UI change that's meant to change them updates the baselines in the
  same change (`pnpm test:visual --update-snapshots`), and the diff shows what moved.
- The browser suites' servers (`playwright*.config.ts`) stop on a request no fake answers
  (`FAKES_FATAL`), so it fails the run at once instead of leaving a page waiting
  on a background job. They serve an Elm build of their own (`ELM_OUTPUT`, built once per run by
  `scripts/elm.ts --to`), and the static build makes one too: neither touches `public/elm/`,
  which `pnpm dev` serves.
- Never run `pnpm test:e2e` and `pnpm test:visual` at the same time, and wait for one to finish
  before starting the other: both build the Elm app into `elm-stuff/builds/test/` and use Vite's
  websocket port, so together they overwrite each other's build and fail in ways that aren't the
  code's. The same goes for leftover servers from a run that was cut short: stop them first.
- Bug fixes come with a test that would have caught them.

### UI

- **Every card shown on a page MUST have a preview** (hover on desktop, tap on touch). Render card
  names with `Card.name`/`Card.nameWith` (or `Card.list` for several, in `src/web/Ui/Card.elm`), never
  as plain text. Reports carry a `cardIndex` with image data for every card they mention
  (`src/server/card-index.ts`): when you add a new list of cards to a report, make sure
  `referencedNames` covers it. Card names fall back to Scryfall's by-name image as a last resort,
  but the index is the source of truth.
- **Cards in copy are explicit references, never guessed from words.** Any text that names cards
  (strategy, swap and land-swap reasons, synergies, how-to-play guides, chat replies and change
  reasons, web research) writes each as `[[Card Name]]` (`src/shared/card-refs.ts`); render it with
  `Card.prose` (or `Ui.Markdown`), which links only those. Never match card names against plain text:
  short names like Six, Bayou or Brawn are also words. Concretely:
  - Every prompt that writes copy includes `CARD_REFS_RULE`; code that writes copy wraps names
    with `ref()`.
  - A reference survives only if it resolves to the report's card index (`settleRefs`, run by
    `writeResults`), and `checkReport` rejects one that doesn't. A card outside the report's own
    lists only gets into the index if it's a Commander-legal card named in full (`isNamedCard`):
    nicknames like "Rift" must not resolve to some other card.
  - A new copy field goes in `mapProse` (`src/server/analysis/prose.ts`), so it's settled, indexed,
    checked and shown as plain words in `report.md`.
  - Chat replies are settled when written (`refSettler` in `src/server/chat.ts`). While a reply
    streams in (`POST /api/decks/:slug/chat` with `Accept: text/event-stream`), it isn't settled
    yet, so the chat previews only references the card index already knows
    (`Card.proseSoFar`); the saved, settled message replaces it when it's done.
- Mobile first: the static site is mainly read on iPhone and iPad. Touch targets ≥ 44px, inputs ≥ 16px
  (no iOS zoom), respect safe areas, card previews must work on tap (no hover dependency).
- The static build is read-only: relative asset paths and a real page for every route, so it works
  on any host and sub-path with no rewrites; no server-only features (upload, re-run) and never
  publish uploaded photos or local paths.
- For visual changes, check screenshots at iPhone (390×844), iPad (820×1180) and desktop widths.
- Elm only draws inside `#root`, so overlays (sheets, dialogs, previews) are drawn at its end, and
  behaviour a view can't express (focus, clipboard, scroll, pointer effects, locale formatting) is a
  custom element in `src/web/elements.ts`, usually an invisible controller inside the element it acts
  on. Keep the page's markup and CSS selectors as they are when adding one.
- Set HTML attributes with `Ui.Attr` (class, href, src, ...), not `Html.Attributes`: when Elm reuses
  an element and a property goes away, it's blanked rather than removed (`class=""`).

### Published content must be readable by agents

- Everything we publish must be accessible to AI agents and other readers that don't run
  JavaScript, starting from whatever link a user copies out of the address bar. On the static site
  every route is a real path (`decks/<slug>/`, `.../optimized/`, `.../rule0/`, see `src/web/routes.ts`),
  and the build writes each one as the app shell with the deck's full report as plain HTML inside
  `#root`, under a `<base>` that points at the site root. Hash links (`#/deck/<slug>`) never reach
  the server, so the app only reads them to move old links onto real paths. There's also an
  `llms.txt` index and `report.md` (all in `src/server/agent-pages.ts`). When you add a route, add its
  page to `deckPaths`.
- The local app keeps hash routes. `src/web/nav.ts` owns the URL; Elm builds links with `Route.href`
  (which mirrors `routeHref` in `src/web/routes.ts`; the parity test keeps them equal) and moves with
  the `navigate` port, never with hand-written `#/` strings.
- `report.md` keeps the deck as submitted and the doc's suggestions apart: Part 1 is only the
  deck as its owner submitted it (its list, stats, bracket, combos and synergies), Part 2 is
  everything suggested (swaps, what they change, combos and synergies they add or break, the
  suggested list). A card the swaps add must never appear in Part 1. Agents read it to answer
  "what does this deck play?", so put new data in the part it describes.
- When you add a section or data to a report, add it to `renderMarkdown` (`src/server/report.ts`) in
  the same change, so the plain page and markdown carry it too; the static build regenerates both
  from `report.json`. Extend the static tests that check these pages.
- Save reports only through `writeResults` (`src/server/storage.ts`): it renders `report.md` from the
  report it saves, so any change to the deck (chat edits, applied suggestions, re-runs) updates the
  markdown too. Never write `report.json` on its own.
- Render model-written text as escaped markdown in these pages, never as raw HTML.
- An owner can publish a deck without the doc's suggestions (`hideSuggestions` in `deck.json`,
  set from the report's toggle or chat). The static build then publishes `withoutSuggestions`
  (`src/server/publish.ts`): only the deck as submitted. When you add a report field derived from the
  suggestions, strip it there, and keep the static test that checks no suggested card leaks.
- Every optimizer run is traced (`src/server/trace.ts`) and saved as the deck's `run.json`, which
  replays at `decks/<slug>/run/`. The run is part of the suggestions: a deck published without
  them publishes no run.

### The optimizer pipeline

- `run` in `src/server/pipeline.ts` is a `TaskGraph` (`src/server/task-graph.ts`): each task names the tasks
  it needs (`Task` enum) and starts as soon as they're done, so independent work overlaps (web
  research runs while Spellbook, EDHREC and the candidate lookups do). A new step declares its
  needs there rather than awaiting in sequence, and reports progress through its `Step`.
- Splitting or merging requests doesn't change what the fakes answer, so tests keep their results;
  check that real runs do too, against the same live data, old code against new.
- Time a real run with `node --import tsx scripts/optimize-bench.ts <slug>`: when each step runs,
  every request by service, and what the run produced, on a copy of the deck.

### Code style

- TypeScript on the server and for the browser glue, strict mode; Elm for the UI. Format with
  prettier and elm-format, lint with oxlint and elm-review (typescript-eslint can't run on
  TypeScript 7, which has no JS compiler API).
- The client's types come from `src/shared/types.ts`: change the TypeScript, run `pnpm gen:elm`, and
  let the Elm compiler show every view the change touches.
- Comments explain _why_, tersely, and only when a future reader needs them. Never leave comments
  about removed or previous code.
- Prefer small pure functions in `analysis/` over logic inside the pipeline or route handlers.
- Don't add in-process caches to hide slow code; make the slow path faster instead.

### Git

- Branches are prefixed `arkham/`. Keep commits focused with descriptive messages.
- Never commit `.env`, `decks/*/uploads`, build output (`dist/`, `site/`) or ad-hoc test decks.
- Run `pnpm check` (and `pnpm test:e2e` for UI changes) before pushing; CI must be green before merging.
